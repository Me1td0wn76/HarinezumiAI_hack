# LT会支援Webアプリ システム設計概要

> チーム内の設計共有用ドキュメント。現時点の決定事項と検討中の項目をまとめる。
> 未決定事項は [open-questions.md](./open-questions.md) を参照。

## 1. システム概要

**システム名（仮）**: LT会支援Webアプリ

**目的**: 学内でLT会を気軽に開催・参加できる環境を構築し、LT会の活性化を図る。

### 解決したい課題

- LT会を開催しても人が集まらない
- 人が集まりそうな日程でしか開催できない
- 主催者と参加者の日程調整に手間がかかる

### 開発方針

- Webシステムを基盤として開発する
- 将来的にスマホアプリへ展開する
- 2〜3人のチームで開発する
- 実際に動作するWebアプリを制作し、発表する

## 2. 主な機能

| 機能 | 内容 |
| --- | --- |
| アカウント管理 | ユーザー登録、ログイン、プロフィール管理 |
| LT会作成 | 発表内容を投稿し、LT会の開催候補を作成 |
| 日程調整 | 参加者がカレンダーから参加可能日を入力 |
| 参加人数集計 | 日程ごとの参加可能人数を集計 |
| 開催日決定 | 主催者が参加可能人数などを参考に開催日を決定 |
| 通知 | 新規LT会や開催日決定などを通知 |
| フォロー | ユーザー同士のフォロー |
| 連絡 | 主催者と参加者が連絡できる仕組み |
| 団体管理 | 団体登録、所属団体ごとのLT会・カレンダー管理 |

※通知方法や連絡機能の詳細は今後決定する。

## 3. 採用アーキテクチャ

### API分離型アーキテクチャ

WebフロントエンドとバックエンドをAPIで接続する構成を採用する。

```
┌─────────────────────────┐
│      Web Frontend       │
│      Next.js            │
└───────────┬─────────────┘
            │ REST API
            ▼
┌─────────────────────────┐
│      Backend API        │
│      NestJS             │
│                         │
│  レイヤードアーキテクチャ │
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│      PostgreSQL         │
└─────────────────────────┘
```

### 採用理由

- Webと将来のスマホアプリでAPIを共有しやすい
- フロントエンドとバックエンドの責務を分離できる
- 2〜3人で担当領域を分けて開発しやすい
- バックエンドの機能を整理・拡張しやすい

## 4. バックエンドの内部設計

### レイヤードアーキテクチャ

NestJSのバックエンドでは、以下のレイヤーを基本とする。

```
┌─────────────────────┐
│ Presentation Layer  │
│ Controller          │
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ Application Layer   │
│ Service             │
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ Data Access Layer   │
│ Repository          │
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ Database            │
│ PostgreSQL          │
└─────────────────────┘
```

### 各レイヤーの役割

| レイヤー | 役割 |
| --- | --- |
| Controller | HTTPリクエストの受付、レスポンスの返却 |
| Service | アプリケーションの処理、業務ルールの実行 |
| Repository | データベースへのアクセス |
| Database | データの保存・管理 |

### 設計方針

- Controllerに複雑なビジネスロジックを記述しない
- Serviceにアプリケーションの処理を集約する
- Repositoryを介してデータベースにアクセスする
- 機能ごとにNestJSのモジュールを分割する

## 6. NestJSを採用する理由

NestJSを採用する根拠として、以下を検討する。

1. **バックエンドの構造化** — モジュール・Controller・Serviceなどの仕組みを利用し、機能ごとにコードを整理する。
2. **API中心の設計** — Webアプリと将来のスマホアプリから利用するAPIを構築する。
3. **TypeScriptの利用** — フロントエンドとバックエンドでTypeScriptを統一する。
4. **レイヤードアーキテクチャとの組み合わせ** — Controller、Service、Repositoryの責務を分離する設計を実装する。

> **注意**: これらはNestJS固有の優位性ではなく、他のフレームワークでも実現できる部分がある。
> 最終的には、チームの経験・開発期間・保守性・実装コストを比較して決定する。

## 8. LT会の開催フロー

```
① 発表者が発表内容を投稿
        ↓
② 開催候補日を設定
        ↓
③ 利用者へ通知
        ↓
④ 参加者が参加可能日を入力
        ↓
⑤ システムが人数を集計
        ↓
⑥ 主催者が開催日を決定
        ↓
⑦ 開催日を参加者に通知
        ↓
⑧ LT会を開催
```

### 開催日の決定方針

システムが候補日ごとの参加可能人数を集計し、主催者が開催日を決定する。
人数だけでなく、発表者の都合や会場の利用状況なども考慮できる設計を目指す。

## A. 最優先で決めること

### A-1. 開発期間とスコープ

設計書のフェーズ1〜4をすべて実装する前提になっているが、機能量に対して期間の記述がない。
2〜3人で日程調整（フェーズ1〜2）まで作り切るだけでも相応の工数になる。

- **推奨**: 発表時点のゴールを「フェーズ1＋2が実際に動く」に固定し、フェーズ3以降は
  デモでは触れず「今後の展望」として扱う。
- 判断材料: 実作業に充てられる日数、メンバーのNext.js / NestJS経験値。

### A-2. 認証方式（設計書では「未決定」）

> **決定（2026-09-21）**: まずメール + パスワードで実装。Google ログイン等は Issue で追加する。
> **更新（2026-09-24）**: Google ログインを追加（#3）。GitHub / X は `apps/api/src/modules/auth/providers/` にプロバイダを足して対応する。
> 同じメールアドレスのアカウントが既にあっても自動では紐付けず 409 を返す（`/auth/register` はメールの所有を確認しないため、自動紐付けは事前乗っ取りにつながる）。

ここが決まらないとフェーズ1が着手できない。

| 候補 | 長所 | 短所 |
| --- | --- | --- |
| ソーシャルログイン（Google / GitHub / X） | 登録の手間がゼロに近い。SNS 的な気軽さに直結する | 外部サービス設定が必要 |
| メール＋パスワード自前実装 | 外部依存なし | ハッシュ・リセット・検証など実装量が多く、事故りやすい |
| Supabase Auth / Clerk など | 実装が最小。ソーシャルログインも付属 | サービス依存、無料枠の制約 |

- **推奨**: ソーシャルログイン（まず Google、次に GitHub / X）。「気軽に参加できる」という目的と直結し、
  登録の心理的ハードルを下げられる。自前のパスワード実装は工数とリスクの割に得るものが少ない。
- ~~学内ドメインで制限する~~ → 対象を全国の誰でもに変更したため不要（2026-09-21）。ドメイン制限は入れない。

### A-3. 「人が集まらない」への機能的な答え

> **決定（2026-09-21）**: Discord Webhook 通知と共有URL（ゲスト回答）の両方を実装した。

設計書の機能一覧は「日程調整の手間」はよく解いているが、**課題①の「人が集まらない」を
直接解く機能がない**。集客はアプリ内通知だけでは解決しない（そもそもアプリを見に来ないため）。

- **推奨（どちらか、あるいは両方）**:
  - 既存チャネルへの通知: Discord / Slack の Webhook にLT会情報を流す。実装コストが小さく効果が大きい。
  - URL共有での回答: ログインなしでも候補日に回答できる共有リンクを持たせる。
- 発表でも「なぜこの機能があるのか」を課題に紐付けて説明できるようになる。
- **前提変更後の補足（2026-09-21）**: 対象が全国の一般ユーザーになったため、Discord Webhook は
  「主催者が自分のコミュニティ（Discord / Slack）に流す」機能として残す。全国規模での「人が集まらない」への答えは
  **発見機能（フォロー・フィード・タグ）** になる。F-1 を参照。

## B. アーキテクチャの再検討

### B-1. API分離型（Next.js + NestJS）が本当に必要か

> **決定（2026-09-21）**: 分離型のまま進める。ブラウザは Next.js のみと通信し、Next.js サーバーが API を呼ぶ（BFF）ので CORS・トークン露出の問題は回避している。

設計書の採用理由のうち「将来のスマホアプリとAPIを共有できる」は、**分離する理由にはならない**。
Next.js の Route Handlers もHTTP APIであり、スマホアプリから同じように呼べる。

実際に分離が効くのは「2〜3人で担当領域を分けやすい」という点。逆に分離のコストは以下。

- リポジトリ／デプロイ先が2つになる
- CORS とクロスオリジンの認証（Cookie or トークン）を自前で扱う必要がある
- フロントとバックで型定義が二重管理になりやすい

| 判断軸 | 分離型（Next.js + NestJS） | 一体型（Next.js のみ） |
| --- | --- | --- |
| 分業のしやすさ | ◎ | △ |
| 初期構築コスト | △ | ◎ |
| 学習・発表での説明価値 | ◎ | ○ |
| スマホ対応 | ○ | ○（差はない） |

- **推奨**: メンバーにバックエンド担当を明確に置けるなら分離型のままでよい。
  期間が短く全員がフロント寄りなら、Next.js 一体型にして日程調整のUI完成度に時間を回す方が
  成果物としては強くなる。**どちらでも成立するので、A-1の期間から逆算して決める。**
- 分離型を選ぶ場合は、monorepo（pnpm workspace など）にして型定義を共有パッケージに置くと二重管理を防げる。

### B-2. Prisma を使う場合の Repository 層

Prisma のクライアント自体がデータアクセスの抽象化を担っているため、その上にさらに
Repository クラスを置くと、多くのメソッドが Prisma の呼び出しを転送するだけになりがち。

- **推奨**: Service から Prisma を直接呼ぶ構成でも、責務分離という設計意図は満たせる。
  ただし「レイヤードアーキテクチャの実装」自体が発表の主題なら、Repository 層を置く意義はある。
  どちらを選ぶにせよ、**理由を説明できる状態**にしておくこと。

### B-3. デプロイ先

設計書に記載がないが、動くものを見せる以上、早い段階で決めておく必要がある。

- **推奨構成（無料枠）**: Next.js → Vercel / NestJS → Render or Railway / PostgreSQL → Neon or Supabase
- 一体型を選んだ場合は Vercel + Neon の2つで済む。

## C. データベース設計の指摘

### C-1. `availability` は3値で持つ

> **決定（2026-09-21）**: `YES / MAYBE / NO` の3値。テーブル名は `date_responses`。

参加可能／不可の2値だと精度が低く、「どの日なら最も集まるか」の判断材料として弱い。

- **推奨**: `○ / △ / ×`（参加可能・調整可能・不可）の3値。調整さん等と同じ感覚で使え、
  主催者の意思決定に必要な情報量が確保できる。
- テーブル名も内容に合わせて `event_date_responses` 等に改めると、何のテーブルか読み取りやすい。

### C-2. 必要な制約とカラム

- `(event_date_id, user_id)` にユニーク制約 — 同一ユーザーの二重回答を防ぐ
- `events` に確定日への参照（`confirmed_date_id`）と状態（募集中／確定／終了）
- `event_dates` は日付だけでなく開始・終了時刻を持たせるか要検討
- 参加可能人数は**カラムで保持せず集計クエリで求める**。回答が更新されるたびに整合性を取る必要がなくなる

### C-3. ゲスト回答を許すかどうか

> **決定（2026-09-21）**: 許す。`user_id` が NULL のときは `guest_key` + `guest_name` で識別する。

A-3 と直結する設計判断。ログイン必須にすると回答率が下がるが、許すと
`user_id` が NULL になり得るため、回答テーブルに表示名カラムが必要になる。**先に方針を決めること。**

### D-1. FullCalendar の用途

日程調整の中心UIは、カレンダーよりも**候補日 × 参加者のグリッド表**（調整さん形式）が適している。
全員の回答状況が一覧でき、どの日が有力か即座に分かるため。

- **推奨**: 候補日の回答＝グリッド表（自前実装で十分）、個人の空き日入力や開催予定の閲覧＝カレンダー、と用途を分ける。
- FullCalendar は core が MIT だが、一部プラグインは有償。使う機能のライセンスを事前に確認すること。

## E. 機能スコープの見直し提案

課題との対応関係を整理すると、優先度は次のようになる。

| 機能 | 対応する課題 | 優先度 |
| --- | --- | --- |
| 日程調整・人数集計・開催日決定 | 日程調整の手間 / 集まる日に開催できない | **必須** |
| LT会作成・一覧 | 前提機能 | **必須** |
| アカウント管理 | 前提機能 | **必須** |
| 外部チャネル通知・共有URL | 人が集まらない | **高**（課題①の唯一の答え） |
| 発見（フィード・タグ・検索） | 人が集まらない（全国規模） | **高** ※前提変更で追加 |
| フォロー | 発見の基礎 | **高** ※前提変更で 低 → 高 |
| 開催形式（オンライン / オフライン） | 全国から参加できる前提 | **高** ※前提変更で追加 |
| 公開プロフィール | SNS 的な体験の土台 | 中 ※前提変更で追加 |
| アプリ内通知 | 人が集まらない | 中 |
| 安全性（通報・ブロック・規約） | 公開サービスの運用 | 中（公開前には必須）※前提変更で追加 |
| 主催者・参加者間の連絡 | 直接対応する課題なし | 低 |
| 団体管理 | 直接対応する課題なし | 低 |

> **2026-09-21 更新**: 当初は学内利用を想定して「フォロー・連絡・団体管理は課題に直接効かない」としていたが、
> 対象を**全国の誰でも**に変更したため、フォロー（#8）は「自分に関係あるLT会を見つける」ための中核機能に格上げし、発見機能（#16）と一体で進める。
> 連絡・団体管理は引き続き低優先。詳細は F を参照。

## F. 全国公開・SNS 型サービスとしての要件（2026-09-21 追加）

前提が「学内利用」から「全国の誰でも使える、SNS のような気軽さのサービス」に変わったことで
新たに必要になる項目。現状の実装（フェーズ1〜2）はそのまま土台として使える。

### F-1. 発見（フィード・タグ・検索）

学内なら一覧を全件並べれば足りたが、全国規模では「自分に関係あるLT会」が見つからないと使われない。
`GET /events` が全件を返す現状のままでは成立しない。

- **推奨**:
  - ホームを「フォロー中の人のLT会」タブと「新着 / 人気」タブに分ける
  - `events` にタグ（`tags: string[]` か `event_tags` 中間テーブル）を持たせ、タグページを作る
  - タイトル・説明の全文検索（PostgreSQL の `tsvector` で十分。外部検索基盤は不要）
  - 一覧はカーソルページネーション（`createdAt, id`）にする

### F-2. 開催形式（オンライン / オフライン）

全国から参加できる前提だと、大半はオンライン開催になる。

- **推奨**: `events` に `format: ONLINE | OFFLINE | HYBRID`、`venue`（会場名・住所）、`meeting_url`（配信URL）を追加。
  `meeting_url` は開催日決定後、回答者にのみ表示する（無関係な人への公開を避ける）。
- 一覧のフィルタ条件にも使う（オンラインのみ、など）。

### F-3. 公開プロフィール

SNS 的な体験には「人」のページが要る。

- **推奨**: `users` に `handle`（`@` で参照する一意の ID、URL に使う）、`avatar_url` を追加。
  `/users/[handle]` で自己紹介・主催したLT会・参加予定を表示し、フォローボタンを置く。
- メールアドレスは引き続き本人以外に返さない（`PublicUserDto` を維持）。

> **実装（2026-09-25、#18）**: `handle`（`^[a-z0-9_]{3,20}$`、小文字で保存、予約語あり）と `avatar_url` を追加し、`GET /users/:handle` と `/users/[handle]` を作成。
> 登録時にハンドルを必須にし、Google ログインでの新規登録はメールアドレスから仮のハンドルを作る。既存ユーザーには `test_user_xxxxxxxxxx` を付けた。
> 「参加予定」は F-8 と同じく候補日に回答したLT会のうち、日程調整中か開催日が未来のもの。
> アバターは https の URL 指定のみで、未設定なら DiceBear でハンドルから生成する（Gravatar はメールアドレスのハッシュを外部に出すため使わない）。アップロードは別 Issue。

- **未決**: ハンドル変更時に旧ハンドルを一定期間予約するか（旧 URL を他人に取られてなりすましに使われるのを防ぐ）。現状は変更した時点で誰でも取れる

### F-4. 安全性と運用（公開前に必須）

誰でも投稿できる以上、公開前に最低限の対策が要る。

- 通報（LT会 / ユーザー）とブロック。通報が溜まったLT会を非表示にできる管理操作
- レート制限（登録・ログイン・LT会作成・回答）。NestJS なら `@nestjs/throttler`
- 利用規約・プライバシーポリシーのページ。登録時の同意
- 共有URL のゲスト回答はスパムに使われ得るため、1 IP あたりの回数制限か簡易 CAPTCHA を検討
- メール認証（登録時の確認メール）は、捨てアカ対策として公開後に必要になる可能性が高い

### F-5. 通知の再設計

- アプリ内通知（Issue #4）を基本にする。全国向けなら Discord Webhook は「主催者が自分のコミュニティに流す」オプション扱い
- メール通知（開催日決定など重要イベントのみ）と、将来の Web Push
- X / LINE への共有ボタン（OGP 画像付きの共有URL）は集客に直接効くので優先度高め

### F-6. 「気軽さ」の UX

- LT会作成の必須入力を最小にする（タイトル + 候補日だけで立てられる。説明は任意 — 現状の実装はこの方針）
- 「気になる」「行きたい」のようなワンタップの反応（回答の前段階のシグナル）
- LT会へのコメント（Issue #9）は SNS 的には優先度が上がる
- 一覧カードに主催者のアバターとタグを出し、タイムラインとして眺められる見た目にする

### F-8. 「参加した LT会」の定義

> **決定（2026-09-24）**: 候補日に1つでも回答したLT会を「参加した LT会」とする。出欠で「参加（YES）」を選んだかは問わない（#15）。

- 対象: `/me` の参加履歴、`GET /users/me/events` の `participated`
- 理由: 日程調整に参加した＝関わったLT会を履歴として見せたい。YES のみに絞ると、調整に協力したが都合が合わなかったLT会が履歴から消える
- 自分が主催したLT会（`organized` 側に出る）と非表示のLT会は含めない。ゲスト回答はアカウントに紐付かないため含まれない
- 実装: `EventsRepository.findManyRespondedBy`（すでにこの定義どおり）
